Checking Low‑Poly Output Quality Without an Answer Key

A photo has many acceptable low-poly versions and no single correct one, so tests cannot compare against an expected image. This study measured how much results vary from run to run, then built a check based on stored scores that caught every fault the author deliberately injected into the code. The faults were a hand-picked set.

Context

lowpoly turns a photo into an image made from flat-coloured triangles, called the mesh. The grid size, the spacing in pixels between starting points, sets how many triangles there are, and triangle size changes the style. So there is no single correct output. Before this work, the four bundled sample outputs were judged by looking at them.

This is the test oracle problem. A test oracle is whatever decides whether a result is correct, and the simplest one is an expected value. Here no expected value exists, and a mesh can be valid and repeatable and still look wrong. Tests have to rely on weaker, partial oracles: rules every output must obey (property tests), a trusted reference version (a differential test), known input-output relations (metamorphic tests) and similarity to the source photo (the baseline check). Human judgement was not used.

Goal
Decide which image-quality checks lowpoly needs, from measurements instead of looking at outputs.
Challenge
Point placement is random, many meshes are acceptable for one photo, and whether an output looks good is a human judgement.
Constraints
Exploratory work. No people rated the images, and the injected faults were chosen by the author.

Outcome

A baseline of stored scores now fails the CI run when a score moves, up or down, by more than the tolerance: 0.005 SSIM or 0.1 dB. It caught every fault and tested size in the author-selected set of 21 injected changes.

Reading the scores. A baseline is a set of scores stored from a known-good version, and the tolerance is the largest change in a score that still passes. CI (continuous integration) runs the tests automatically on several systems whenever the code changes. SSIM, the structural similarity index, runs from 0 to 1, and higher means closer to the source photo in local shape, contrast and brightness. PSNR, peak signal-to-noise ratio, is reported in decibels (dB), and higher means a smaller average colour error. Spread is how much a measure varies: across repeated runs (standard deviation) or across systems (platform spread).

  • 0.002–0.0060.002 to 0.006

    SSIM standard deviation (typical spread) across 20 seeds, which fix the random point placement. For PSNR it is 0.1 to 0.3 dB. This noise floor means smaller differences are not real.

  • 0.0007

    SSIM at most, with 0.02 dB, of platform spread (the difference between operating systems and library versions) across nine CI environments. That is 7 and 5 times below the tolerances.

  • 0.32–0.780.32 to 0.78

    SSIM against the source across the settings of the four sample photos, so no fixed pass mark can work.

  • Both measures are needed. Large faults (wrong photo, shifted output) moved both. Small faults (darker colours, a blackened border row) barely moved SSIM but showed in PSNR.
  • Compare, do not threshold. At grid 16, each photo scored 0.17 to 0.45 higher against its own source than against the best of the other three photos, and a margin of 0.10 holds for these four photos.
  • Seeds must be pinned. A pinned seed is fixed, so every run places points the same way. The tolerances sit inside the seed-to-seed noise range, so unpinned seeds would trip them. They were tightened after misses on this set, and the smallest sizes are caught with thin margins.
  • Platforms agree closely. Linux, Windows and Intel macOS match the stored scores exactly. Apple silicon differs slightly.
  • Settings that follow edges best. Edge lift measures how closely the mesh follows the photo's edges, with the chance level (what the measure gives with no edge-following at all) subtracted. Jitter is how far a point may move from its grid position. Edge lift peaks at about 16 cells across the long side (the longer image side divided by the grid size) with jitter at half the grid, and at a 16 px grid with the package's fixed 12 px jitter. The package defaults are unchanged.

Not established: which output people prefer. The detection rate comes from a hand-picked fault set, so it is not a general estimate of effectiveness. Edge-following is not appeal.

Key stages

  1. 1

    Measure noise and known faults

    Twenty seeds per photo gave the noise floor, the run-to-run variation with settings unchanged. Damaging one cat output in known ways showed which measure sees which fault: a different photo moved SSIM by −0.310 and PSNR by −10.43 dB, while a blackened last row and column moved SSIM by only −0.001 and PSNR by −0.61 dB.

  2. 2

    Prefer relative checks to absolute ones

    A coarser mesh scores lower by design, so a fixed pass mark would reject good coarse output or accept bad dense output. A stored reference per photo and setting avoids this.

  3. 3

    Build the baseline

    Stored scores for four sample photos at two settings (the default and a 16 px grid) became a test with two-sided tolerances of 0.005 SSIM and 0.1 dB, meaning a rise fails as well as a drop. Updating the scores is a reviewed change.

  4. 4

    Validate it by fault injection

    Fault injection means changing the code on purpose and checking whether the tests notice. The existing tests other than the differential test, which compares the current output with a trusted reference version, caught 3 of the 9 faults. The differential test caught every change, harmless ones included, so it cannot tell a fault from an intended change. The baseline caught every injected fault and tested size, tolerated one of the two harmless changes and flagged the other.

  5. 5

    Try metamorphic relations

    A metamorphic test changes the input in a known way and checks that the output changes as expected, without knowing the exact correct output. A prototype of three such relations caught 6 of 12 injected faults, and the baseline caught all six too. It adds no detection, and whether it helps diagnose a fault was not measured.

Learning

  • Measure the normal variation before using a score to flag changes.

    SSIM and PSNR catch different errors, and the noise floor decides what counts as a real change.

  • Validate a check by injecting faults before trusting it.

    Injection showed which checks add detection and which do not. It came last in this project and could have followed the first baseline at once.

  • A baseline has to fail in both directions.

    Ignoring the saturation option (colour intensity, where 1.0 leaves colours unchanged) raised SSIM and PSNR on every photo, so a check that fails only on a drop would miss it.

  • Keep tuning studies apart from regression checks.

    The grid and parameter sweeps answered which defaults to use, and no regression check, which looks for a change that makes something worse, relies on them.

  • Match the evidence to the claim.

    Numeric stability needs platform data and appeal needs people. The list of proposed tests was longer than the evidence supported, and most are still unbuilt.

Next steps

The source gives no dates or owners. The baseline is built; everything below is proposed or not done.

  • Five checks proposed, not built. Colour options do not move the mesh. Jitter 0 stops points snapping to edges. The quality measures detect damage. Relation checks: a photo must beat the best other photo by at least 0.10 SSIM, and grid 9 must beat grid 40 by at least 0.05. Raising saturation above 1 changes the colours.
  • Defaults, not adopted. A 16 px grid and a jitter of max(12, grid / 2), the larger of 12 px and half the grid, are suggested. The Canny thresholds (100/200) and the smoothing strength (75) stay. Canny is an edge detector, and its low and high thresholds set how sensitive it is: a pixel counts as an edge when its brightness change is above the high value, or above the low value and connected to one that is. Smoothing is a bilateral filter that blurs flat areas while keeping edges, and 75 is its strength.
  • Not done. A human preference comparison. The CI flake rate (how often a run fails without a real change), the effort of updating the baseline and user impact were also not measured.
